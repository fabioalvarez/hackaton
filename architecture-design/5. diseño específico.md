## 1. API

**Viene de:** Instancias del servicio de consulta (contenedores de Docker Compose).

| # | Requerimiento | Origen |
|---|---|---|
| A1 | Responder la consulta de pedidos e indicar la versión de los datos en un header | RF-01, RF-02 |
| A2 | Responder la página de inicio | RF-03 |
| A3 | Informar su estado de salud | RF-04, QA-01 |
| A4 | Indicar en cada respuesta qué instancia la atendió | RF-05, QA-06 |
| A5 | Leer los datos desde el almacenamiento compartido, sin guardar estado propio | QA-01, QA-03 |
| A6 | Registrar cada solicitud con el ID de instancia | QA-06 |
| A7 | Tomar su configuración desde fuera de la imagen | CT-01 |
| A8 | Empaquetarse en una imagen con versión fija | QA-04 |
| A9 | Que una versión defectuosa falle su salud, para que el despliegue vuelva a la anterior | QA-04 |

### 1.1 Stack

| Decisión | Valor |
|---|---|
| Lenguaje | Python 3.12 |
| Framework | FastAPI (servidor ASGI: uvicorn) |
| Gestión de paquetes | `uv` (`pyproject.toml` + `uv.lock` versionado; `uv sync --frozen` en la imagen) |
| Estado | Stateless: sin caché ni variables globales mutables; cada solicitud lee el archivo de datos |

### 1.2 Contrato (A1–A4)

Solo `GET`. Cualquier otro método responde `405`; cualquier otra ruta, `404`. Cada dato de la respuesta viaja en **un solo sitio, sin repetirse**. La instancia que atendió va en el header `X-Instance-Id` (A4) de toda respuesta, y la versión de los datos va en el header `X-Data-Version` de `/orders` y `/health`; el cuerpo JSON no repite ninguno de los dos. Las respuestas son JSON UTF-8, salvo las páginas HTML (ver abajo). Todo el contrato (rutas, campos, valores y mensajes de error) está en inglés.

| Operación | Ruta | Respuestas | Req. |
|---|---|---|---|
| Inicio | `GET /` | 200 | RF-03 |
| Salud | `GET /health` | 200, 503 | RF-04 |
| Pedidos | `GET /orders` | 200, 503 | RF-01, RF-02 |
| Cualquier otra ruta | — | 404 | RF-05 |

**Páginas y JSON en la misma dirección.** `/` solo existe como página. `/orders` y `/health` sirven **el JSON** a un programa (`curl`, el balanceador, la herramienta de verificación: no piden HTML) y **una página HTML** a un navegador (su `Accept` incluye `text/html`). Así el contrato de los datos no cambia y las páginas son otra vista de lo mismo. Las respuestas llevan `Vary: Accept`.

Todas las páginas son un solo archivo HTML con su CSS y su JavaScript dentro: no cargan nada de afuera (CT-02), se ven en claro y en oscuro y se adaptan al ancho de la pantalla. Comparten un menú (Home, Orders, Health) y al pie dicen qué instancia las sirvió (RF-05). El nombre del servicio y el de la instancia se escapan, para que no puedan inyectar HTML. Los textos están en inglés, como el resto del contrato.

| Página | Muestra | Requisito |
|---|---|---|
| `/` (Home) | Solo confirma que es el servicio correcto: el nombre (`SERVICE_NAME`) y dos botones hacia las demás páginas. No muestra pedidos ni estado | RF-03 |
| `/orders` | La versión de los datos, el número de pedidos y la tabla de pedidos con su estado en colores. Los pide al JSON de la misma dirección | RF-01, RF-02 |
| `/health` | Si el servicio está disponible (verde o rojo) y la versión de los datos. Se vuelve a comprobar cada 5 s. La página carga aunque los datos estén perdidos; lo que muestra es que no está disponible | RF-04 |

**`GET /health`** → `200`

Header `X-Data-Version: data-v1`

```json
{
  "status": "ok"
}
```

**`GET /orders`** → `200`

Header `X-Data-Version: data-v1` (la versión de los datos de esos pedidos, RF-02)

```json
{
  "orders": [
    { "id": "ORD-001", "zone": "North", "status": "in_transit" },
    { "id": "ORD-002", "zone": "Center", "status": "delivered" }
  ]
}
```

**`/health` o `/orders` con datos ilegibles o inválidos** → `503`

```json
{
  "status": "data_error"
}
```

**Ruta inexistente** → `404`

```json
{
  "error": "Route not found"
}
```

| Aspecto | Definición |
|---|---|
| Valores de `status` de un pedido | `pending`, `preparing`, `in_transit`, `delivered` |
| Parámetros de entrada | Ninguno; sin paginación (6 pedidos, el reto no pide filtros) |
| Contenido de `/orders` | Los pedidos tal como están en el archivo, sin transformarlos (deben coincidir al 100 % con el respaldo, QA-02/QA-03). Por eso el archivo usa los mismos nombres de campo en inglés (sección 2). La versión del archivo no va en el cuerpo: va en el header `X-Data-Version` |
| `/docs`, `/redoc`, `/openapi.json` | Desactivadas (CT-02: superficie mínima); responden `404` con el mismo formato |

### 1.3 Lectura de datos (A5)

| Aspecto | Definición |
|---|---|
| Ruta del archivo | Variable `DATA_PATH`. En el despliegue apunta al archivo dentro del volumen `orders-data`, montado en solo lectura en el contenedor (`/data/orders.json`); en las pruebas unitarias, a un archivo temporal |
| Cuándo se lee | En **cada solicitud** a `/orders` y `/health`. Una versión nueva cargada en el volumen se ve en ambos contenedores sin reiniciarlos, y no hay estado local que perder |
| Validación | JSON válido; objeto con `data_version` (string no vacío) y `orders` (lista) |
| Si la validación falla | Archivo ausente, ilegible o inválido → `503 data_error` |
| Implementación | Función síncrona (`def`, no `async def`): FastAPI la ejecuta en su threadpool sin bloquear el loop |

### 1.4 Identificación de la instancia (A4)

| Aspecto | Definición |
|---|---|
| Origen del ID | Variable `INSTANCE_ID`; si no está definida, el nombre de host, que en Docker es el ID del contenedor (único por instancia) |
| Si no está definida | `socket.gethostname()` (en Docker es el ID del contenedor, único por instancia) |
| Dónde aparece | Solo en el header `X-Instance-Id`, en **toda** respuesta (también 404, 405 y 503). El cuerpo no lleva el campo. La versión de los datos va aparte, en `X-Data-Version` |
| Cómo se añade | Un middleware |

### 1.5 Salud (A3, A9)

| Aspecto | Definición |
|---|---|
| Cuándo responde `ok` | Solo si **puede leer y validar los datos**, no solo si el proceso vive |
| Quién la consulta | `healthcheck` de Compose y el script de despliegue; HAProxy la sondea por su cuenta (§4) |
| Versión defectuosa (A9) | Debe fallar este chequeo (no arranca o devuelve 503) para que el script de despliegue no la dé por sana y revierta. Cómo se provoca en la prueba: sección 5 |
| Dependencias | Ninguna externa; solo el archivo de datos |

### 1.6 Registro de solicitudes (A6)

| Aspecto | Definición |
|---|---|
| Formato | Una línea JSON por solicitud, escrita por un middleware |
| Destino | stdout; lo recoge Docker (`docker compose logs`) |
| Campos | `ts` (ISO 8601 UTC), `instance` (mismo valor del header), `method`, `path`, `status`, `ms`, `data_version` (la del header `X-Data-Version` de la respuesta; vacía si la solicitud no leyó datos) |
| Logs de uvicorn | Se redirigen al mismo formato JSON |
| Consultas | Sección 7 |

## 2. Persistencia

**Viene de:** volumen nombrado de Docker, Externalized State (QA-03).

| Aspecto | Definición |
|---|---|
| Formato del archivo | JSON: `data_version` (string) y `orders` (lista de `id`, `zone`, `status`); es `next/store/data/orders.json`, que ya cumple el contrato de §1.2 |
| Volumen | `orders-data`, creado por Compose |
| Montaje | `/data` en las réplicas de `api`, con `:ro` |
| Carga inicial | `make load-data`: un contenedor temporal (`alpine`) monta el volumen en escritura y copia `store/data/orders.json`. Junto con el contenedor `backup`, es lo único que escribe en el volumen; nada pasa por la API |
| Carga de una versión nueva | `make load-data FILE=<ruta>`: copia el archivo al volumen y las 2 instancias lo ven en la siguiente solicitud; el respaldo lo hace solo el contenedor `backup` (§3). La versión nueva debe llevar un `data_version` distinto |
| Persistencia | `make down` borra el volumen (QA-07); recrear o actualizar contenedores (`docker compose up --force-recreate`) lo conserva (QA-03) |

## 3. Respaldo y restauración

**Viene de:** contenedor `backup`, Backup & Restore (QA-02), según el [diseño arquitectónico §5](3.%20diseño%20arquitectónico.md). Es automático y no lo hace la API (volumen de solo lectura, CT-02) ni una persona.

| Aspecto | Definición |
|---|---|
| Quién | Servicio `backup` de Compose (`next/backup/src/`, comando `python main.py`), que arranca con `make up`. Es el único con escritura sobre el volumen |
| Implementación | Script de Python (solo biblioteca estándar) en una imagen `python:3.12-slim` (`next/backup/Dockerfile`) |
| Frecuencia | Revisa el archivo cada `INTERVAL` = 5 s |
| Nombre de la copia | `backups/orders-<data_version>.json` (por ejemplo `orders-data-v1.json`); la versión se lee del propio archivo |
| Dónde | `next/store/backups/`, fuera del volumen de trabajo y en `.gitignore` |
| Memoria | `orders-<versión>.sha256` (hash de cada copia) y `latest` (última versión válida vista) |
| Validación | La misma que la API (§1.3): JSON con `data_version` no vacío, `orders` como lista y `status` válido. Además `data_version` solo admite letras, números, `.`, `_` y `-`, porque forma parte del nombre del archivo |

Ciclo de cada revisión:

1. Lee y valida `/data/orders.json`.
2. **Válido y sin copia de esa versión** → copia el archivo a `store/backups/` (respaldo de la versión nueva).
3. **Válido, con copia y mismo hash** → no hace nada.
4. **Válido, con copia pero distinto hash** → actualiza el respaldo de esa versión: un cambio en datos válidos es una actualización, no una pérdida.
5. **Ausente o inválido** → restaura la última versión válida (`latest`).
6. **Sin ninguna copia disponible** → registra un error y reintenta; no inventa datos.

| Aspecto | Definición |
|---|---|
| Restauración | Copia el respaldo a un archivo temporal dentro del volumen y lo renombra sobre `orders.json`: el reemplazo es de una sola vez, y las instancias nunca leen un archivo a medias |
| Verificación | No hay un paso aparte. Si la copia falló, la siguiente revisión detecta el archivo inválido y restaura de nuevo. La comparación de versión y contenido contra el respaldo es la evidencia de la prueba PR-04 |
| Medición del tiempo | Cada restauración registra `took Ns`; la recuperación completa es la detección (≤ 5 s) más la copia. Meta ≤ 5 min |
| Carga de datos | `make load-data` copia a un archivo temporal y lo renombra, para que el vigilante no lea un archivo a medias |
| Pérdida de datos para la prueba | `make corrupt` deja el archivo inválido y `make delete-data` lo borra; ambos solo para PR-04 (Makefile, sección de validación) |
| Logs | Una línea JSON con solo `level` y `detail`, que cuenta el proceso: `docker compose logs backup`. En `info` salen las acciones (`new data version v2, starting backup` y `backup done`; `data is different from the backup of v1, starting backup` y `backup done`; `data file is missing or invalid, starting restore of v1` y `restore done in 0.0s`); en `error`, los fallos. En `debug` (variable `LOG_LEVEL`) salen además `starting backup process` y, si todo está igual, `data file is the same as the backup of v1, no backup is required` |
| Límite | `store/backups/` está en el mismo equipo: cubre la pérdida del archivo de datos, no la pérdida del disco |

## 4. Balanceador y salud

**Viene de:** HAProxy, Redundancia activa (QA-01). Por qué HAProxy y no nginx: [local components §4](4. local componentse.md).

| Aspecto | Definición |
|---|---|
| Puerto publicado | `8000` → `8080` de HAProxy; es el único puerto publicado (CT-02) |
| Reparto | `balance roundrobin` entre las instancias que HAProxy descubre con el DNS de Docker: el nombre `api` apunta a todas las réplicas (`server-template` de 4 puestos: 2 réplicas más 2 durante un despliegue) |
| Sondeo de salud | Activo: `option httpchk GET /health` con `http-check expect status 200`, cada 5 s |
| Salida de una instancia | `fall 2`: tras 2 sondeos fallidos seguidos (≈ 10 s) deja de recibir solicitudes |
| Regreso de una instancia | `rise 2`: tras 2 sondeos correctos vuelve al reparto |
| Reintento | `retries 3`, `option redispatch` y `retry-on conn-failure empty-response`: si una conexión falla antes de detectar la caída, o llega a una instancia nueva que aún no está lista, la solicitud se reenvía a otra instancia |
| Tiempos | `timeout connect 1s`, `timeout server 3s` (una instancia colgada no retiene la solicitud) y `timeout client 5s` |
| Header de instancia | HAProxy no lo modifica: pasa el `X-Instance-Id` de la API |
| Healthcheck de Compose | Cada contenedor define uno (`GET /health` cada 5 s, 2 reintentos). No reparte tráfico: sirve para ordenar el arranque, para `make up --wait` y para el rollback (§5) |
| Arranque | `depends_on` con `condition: service_healthy`: HAProxy arranca cuando las 2 instancias están sanas |
| Descubrimiento | `resolvers docker` (DNS de Docker, `hold valid 5s`) e `init-addr none`: HAProxy vuelve a resolver `api` cada pocos segundos y detecta solo los contenedores que se crean o se eliminan |
| Logs | `option httplog` a stdout: cada línea indica el servidor que atendió (`api/api1`) |

## 5. Despliegue y rollback

**Viene de:** script de despliegue en Python (`next/deploy/`), Rollback automático (QA-04). Por qué contenedores nuevos al lado de los viejos: [local components §8.2](4. local componentse.md).

| Aspecto | Definición |
|---|---|
| Imagen | `next-api:<versión>`, construida con `next/api/Dockerfile` (contexto `next/api/`); la etiqueta se pasa a Compose con la variable `TAG` |
| Comando | `make deploy TAG=1.1.0` (la etiqueta es obligatoria) |
| Versión vigente | `.deploy-history` guarda una etiqueta por línea; la última es la que corre. `make up` la usa, o `dev` si no existe |
| Imágenes conservadas | Las de las últimas 5 versiones del historial; las demás se borran |

Flujo de `make deploy`:

1. Borra los contenedores que quedaron sin correr de un despliegue fallido.
2. Construye `next-api:$TAG`.
3. Crea 2 contenedores más con `docker compose up --no-recreate --scale`: hay 4 corriendo, y los 2 actuales no se tocan. Siempre se crean 2, aunque hubiera menos réplicas vivas.
4. Espera hasta 2 min a que los 2 nuevos queden *healthy*.
5. Espera a que HAProxy ya responda con los IDs de los 2 nuevos (consulta `/health` por HAProxy y mira el header `X-Instance-Id`). *Healthy* no basta: HAProxy tarda unos segundos en descubrirlos.
6. **Si todo funciona:** elimina los 2 viejos, guarda la etiqueta en el historial y borra las imágenes antiguas.
7. **Si no arrancan, no quedan sanos o HAProxy no los usa:** elimina los 2 nuevos, imprime los logs del que falló, termina con error y no cambia el historial. Los viejos nunca se detuvieron, así que el servicio no se interrumpe y los datos no se tocan.

**Versión defectuosa para la prueba (PR-05):** `make deploy TAG=bad BREAK=1` (o `make deploy-broken`) construye la imagen con `--build-arg BREAK=1`, que elimina el comando `next`: el contenedor no arranca. No se agrega ningún código de falla a la aplicación. El `DATA_PATH` no sirve para esto, porque Compose lo fija y gana sobre el de la imagen.

## 9. Verificación de requisitos

**Viene de:** la necesidad de demostrar que todos los requisitos funcionales, escenarios de calidad y constraints se cumplen. Es una herramienta en Python (`next/verify/`) que causa el estímulo de cada escenario sobre el entorno levantado, mide la respuesta y la compara con el criterio de los archivos 1 y 2.

| ID | Qué hace la herramienta | Criterio |
|---|---|---|
| RF-01 a RF-05 | Consulta `/orders`, `/`, `/health` por HAProxy | 6 pedidos; versión igual a la de los datos cargados; 200 y "ok"; `X-Instance-Id` en toda respuesta y las 2 instancias aparecen |
| QA-01 | Detiene una instancia con tráfico continuo (una solicitud cada 0,1 s) | ≥ 99 % de éxito; HAProxy la saca en ≤ 10 s (se mide con su log) |
| QA-06 | Con el mismo incidente, busca la causa solo con `docker compose ps` y el log de HAProxy | Instancia identificada en ≤ 120 s; 100 % de las solicitudes asociadas a una instancia |
| QA-02 | Deja inválido el archivo de datos y luego lo borra | Restaurado sin intervención en ≤ 5 min; hash igual al del respaldo (versión y contenido idénticos) |
| QA-03 | Elimina un contenedor y espera a que se recree | Mismos pedidos y versión antes y después; 0 perdidos |
| QA-04 | Despliega una versión buena y luego una defectuosa, con tráfico continuo | La defectuosa se descarta en ≤ 5 min; la versión vigente no cambia; 0 solicitudes fallidas; datos iguales |
| QA-05 | `make down` y `make up`, cronometrado | Operativo con las 2 instancias en ≤ 10 min con un solo comando |
| QA-07 | `make down` y revisa contenedores, redes y volúmenes del proyecto; revisa la sección de costo | 0 recursos en ≤ 15 min; factor de consumo documentado para cada componente |
| CT-01 | Busca claves, llaves privadas y contraseñas en los archivos del repositorio y en la imagen | Ninguna; `.env` ignorado por git; sin `.env` ni datos dentro de la imagen |
| CT-02 | Revisa los puertos publicados, intenta acceder directo a la API y a `/docs` | Solo HAProxy publica un puerto; la API no responde directo; `/docs`, `/redoc` y `/openapi.json` dan 404 |
| TESTS | Ejecuta `make test` | Todos pasan (evidencia adicional de RF, QA-02, QA-03, QA-04, QA-06 y CT) |

| Aspecto | Definición |
|---|---|
| Comando | `make verify`; `YES=1` omite la pregunta, `STEP=1` espera un Enter antes de cada escenario y `ONLY=QA-01,RF-02` ejecuta solo algunas |
| Requisito previo | El entorno levantado con `make up` (salvo para QA-05 y QA-07, que lo levantan ellos) |
| Orden | Primero las que no cambian nada (RF, CT, tests); después las que sí (QA-01 a QA-07) |
| Confirmación | Antes de las que cambian el entorno pregunta; sin terminal interactiva exige `--yes` |
| Al terminar | El entorno queda levantado. El `make down` de QA-05 y QA-07 borra el volumen de datos, que vuelve a los datos iniciales de `store/data/orders.json`; lo cargado con `make load-data` se pierde. `store/backups/` no se borra |
| Salida en vivo | Antes de cada escenario dice qué hará y el criterio. Durante el escenario muestra cada llamada a la API (hora, ruta, código e instancia que respondió: una solicitud cada 0,25 s) y lo que le pasa al entorno, tomado de `docker events`, del log de HAProxy y del log del vigilante: contenedores que se detienen, crean o quedan sanos, instancias que HAProxy saca o reincorpora, restauraciones de datos y pasos del despliegue |
| Salida final | Veredicto de cada escenario con lo medido, un resumen de una línea por requisito, e informe `validations/verification.md` con la evidencia (solo en una ejecución completa; una parcial, con `ONLY=`, no lo actualiza), en la raíz del repositorio y versionado: es la evidencia de las pruebas que pide el reto |
| Código de salida | 0 si todo cumple; 1 si algo no cumple |
| Si una comprobación falla por un error | Se reporta como no cumple con el error y las demás siguen |
| Límite | QA-05 no borra `.env` ni `api/.venv`: parte de un entorno sin contenedores, no de un equipo sin configuración |
| Gasto de QA-07 | Se declara 0: todo corre en la máquina local y no se usa ninguna cuenta de nube |

### 9.1 Cómo está organizado el código

| Archivo (`next/verify/src/`) | Qué hace |
|---|---|
| `main.py` | La entrada: lee las opciones, elige las pruebas, pregunta si hace falta, las ejecuta en orden y escribe el informe |
| `checks_functional.py` | RF-01 a RF-05 |
| `checks_constraints.py` | CT-01, CT-02 y los tests automáticos |
| `checks_quality.py` | QA-01 a QA-07, escenarios que cambian el entorno |
| `result.py` | Qué es un requisito (`Requirement`: ID, título y criterio, una sola vez) y qué reporta una prueba (`Result`). El decorador `@check` dice qué requisitos prueba una función, si cambia el entorno y si lo necesita levantado |
| `commands.py` | Ejecutar comandos como lo hace `make`, con las versiones desplegadas |
| `service.py` | Hablar con el servicio (`get`), enviar tráfico (`Traffic`) y esperar (`wait_until`) |
| `environment.py` | Contenedores, datos del volumen y el log de HAProxy |
| `live.py` | Solo imprime: líneas con hora, encabezados y veredictos |
| `watching.py` | Cuenta en palabras lo que hace el entorno mientras corre un escenario: contenedores, HAProxy y vigilante |
| `report.py` | El resumen final y el informe en Markdown |

Cada requisito se declara una vez, arriba de su prueba. Cada escenario de calidad sigue el mismo guion: empezar con el servicio funcionando, provocar el estímulo contando lo que se hace, medir y reportar.
