# Local components — Nodo Ruta (entorno local)

Equivalente local de los [cloud components](4.%20cloud%20components.md). No hay tiempo ni cuenta para desplegar en la nube, así que el desarrollo y las pruebas se hacen en una sola máquina con contenedores. El [diseño arquitectónico](3.%20diseño%20arquitectónico.md) no cambia: cada pieza de AWS se sustituye por una local que cumple el mismo rol y el mismo escenario de calidad.

Valoración: **Cumple** · **Parcial** · **No cumple**.

---

## Resumen de lo seleccionado

| Decisión del diseño arquitectónico | Componente en AWS | Componente local | Configuración |
|---|---|---|---|
| Lógica síncrona | HTTP/REST sobre ALB | HTTP/REST sobre HAProxy | `GET /orders`, `GET /`, `GET /health` |
| QA-01 Redundancia activa (cómputo) | ECS Fargate, 2 tareas | Docker Compose, servicio `api` con 2 réplicas | Misma imagen (`next/api/Dockerfile`, Python 3.12, FastAPI, puerto 8080) |
| QA-01 Redundancia activa (balanceo) | ALB | HAProxy | Sondeo activo de `GET /health` cada 5 s; saca la instancia tras 2 fallos seguidos (≈ 10 s) |
| QA-02 Backup & Restore | Copia a S3 con versionado | Contenedor `backup` (vigilante) + carpeta local `store/backups/` con la versión en el nombre | Corre solo: respalda cada versión nueva y restaura si los datos se pierden o se alteran; revisa cada 5 s |
| QA-03 Externalized State | EFS | Volumen nombrado de Docker | Montado en solo lectura (`:ro`) en los 2 contenedores |
| QA-04 Rollback automático | ECR + circuit breaker de ECS | Etiquetas de imagen locales + script de despliegue con espera de salud | Imágenes `next-api:v1`, `v2`…; se conservan las últimas 5 |
| QA-05 Infraestructura como código | Terraform | `docker-compose.yml` + `Makefile` | `make up` crea, `make down` destruye |
| QA-06 Monitor / Logging | CloudWatch Logs | `docker logs` / `docker compose logs` | Una línea JSON por solicitud con `instance_id` |
| QA-07 Cost Efficiency | Destrucción con Terraform | Recursos locales: costo 0 | `make down` elimina contenedores, red y volumen |
| CT-01 Sin secretos | SSM Parameter Store | Variables de entorno, sin archivo `.env` versionado | Hoy no hay secretos |
| CT-02 Exposición mínima | Solo el ALB recibe tráfico | Solo HAProxy publica puerto | `localhost:8000`; los contenedores `api-*` no publican puerto |

**Requisito previo:** Docker (con Docker Compose v2) y `make`. No se necesita cuenta ni conexión a ninguna nube.

## 1. Topología

```
Cliente (curl / navegador / pruebas)
        │  localhost:8000
        ▼
   ┌─────────┐   sondea /health cada 5 s
   │ HAProxy │──────────────┬──────────────┐
   └─────────┘              ▼              ▼
                        ┌───────┐      ┌───────┐
                        │ api   │      │ api   │      2 réplicas en la red interna
                        └───┬───┘      └───┬───┘      de Compose (sin puertos publicados)
                            └──────┬───────┘
                                   ▼  (solo lectura)
                        Volumen `orders-data`  ◄──► contenedor `backup` ──► store/backups/orders-<versión>.json
                                               (único con escritura; vigila, respalda y restaura solo)
```

## 2. Lógica

El contrato del servicio no cambia respecto a la nube (ver [cloud components §1](4.%20cloud%20components.md)).

| Operación | Respuesta | Cubre |
|---|---|---|
| `GET /orders` | Los pedidos y el identificador de versión | RF-01, RF-02 |
| `GET /` | Página de inicio | RF-03 |
| `GET /health` | Estado "ok" | RF-04 |
| Toda respuesta | Header `X-Instance-Id` | RF-05 |

**Identificador de instancia:** en AWS es el ID de la tarea; en local es el ID del contenedor (por ejemplo `3f9a1c7e2b40`), que es el nombre de host y el valor por defecto de `INSTANCE_ID`.

## 3. Cómputo

**Viene de:** 2 instancias sin estado (QA-01), recreación de contenedores (QA-03).

| Opción | 2 instancias de la misma imagen | Reemplazo automático | Crear y destruir con un comando | Costo |
|---|---|---|---|---|
| **Docker Compose** | Cumple | Cumple (`restart: unless-stopped`) | Cumple | 0 |
| Kubernetes local (kind / minikube) | Cumple | Cumple | Parcial: más piezas que instalar y configurar | 0 |
| `docker run` manual | Cumple | No cumple | No cumple | 0 |

**Selección: Docker Compose.** Es lo mínimo que cumple QA-01, QA-03 y QA-05; el reto no exige un orquestador concreto.

**Diferencia con AWS:** las 2 instancias corren en la misma máquina, por lo que no se prueba la caída de una zona de disponibilidad; solo la caída de una instancia, que es lo que pide QA-01.

## 4. Punto de entrada y salud

**Viene de:** balanceador con health checks activos, redundancia activa (QA-01): "comprueba la salud y deja de enviar solicitudes a la instancia que falla".

| Opción | Reparte entre las 2 instancias | Comprueba `/health` por sí solo (sondeo activo) | Configuración sencilla en Compose |
|---|---|---|---|
| **HAProxy** | Cumple | Cumple (`check inter 5s fall 2`) | Cumple |
| nginx (versión libre) | Cumple | No cumple: solo detecta fallos en solicitudes reales (pasivo) | Cumple |
| Traefik | Cumple | Cumple | Parcial: configuración por etiquetas, menos explícita |

**Selección: HAProxy.** Se elige sobre nginx porque el diseño pide un balanceador que *compruebe* la salud, y la versión libre de nginx no puede hacerlo:

- **nginx** solo se entera de una falla cuando una solicitud real falla. Sin tráfico no detecta la caída, y la medida de QA-01 (máximo 10 s hasta dejar de enviar solicitudes) dependería de que haya consultas en curso. El sondeo activo en nginx exige nginx Plus (de pago) o compilar un módulo de terceros.
- **HAProxy** consulta `GET /health` en cada instancia cada 5 s, saca la instancia tras 2 fallos seguidos (≈ 10 s) y la reincorpora tras 2 aciertos. Es exactamente la medida de QA-01, con o sin tráfico, y usa la misma ruta que el diseño define para la salud (RF-04).

```
backend api
    balance roundrobin
    option httpchk GET /health
    http-check expect status 200
    default-server check inter 5s fastinter 1s fall 2 rise 2 resolvers docker init-addr none
    server-template api 4 api:8080
```

- **Cómo cumple QA-01:** HAProxy deja de enviar solicitudes a la instancia que falla el sondeo. Si una conexión falla antes de detectar la caída, o llega a una instancia nueva que aún no está lista, `retries 3` y `option redispatch` la reintentan en otra instancia, así que el cliente no ve el error (≥ 99 % de éxito).
- **Reincorporación:** una instancia que vuelve a responder `/health` con 200 entra de nuevo tras 2 sondeos correctos.
- **Descubrimiento de instancias:** el nombre `api` apunta a todas las réplicas en el DNS de Docker. HAProxy lo consulta cada pocos segundos (`resolvers docker`, `server-template` de 4 puestos: 2 réplicas más 2 que existen durante un despliegue). Los contenedores que un despliegue crea o elimina se detectan solos, sin tocar la configuración.
- **Salud visible:** el estado de cada instancia se ve en los logs de HAProxy (`Server api/api1 is DOWN`) y en `docker compose ps`.
- **Healthcheck del contenedor:** cada instancia además lleva un `healthcheck` de Compose contra `/health`. Es otra cosa: no reparte tráfico. Sirve para que HAProxy arranque cuando las réplicas están sanas, para que `make up` espere a que estén listas y para decidir si un despliegue nuevo funciona (§8.2).

## 6. Respaldo y restauración

**Viene de:** Backup & Restore (QA-02). Debe ser automático: nadie ejecuta comandos para respaldar ni para recuperar.

| Opción | Automático | Fuera de la API (solo lectura, CT-02) | Componentes extra |
|---|---|---|---|
| **Contenedor `backup` que vigila el volumen** | Cumple: respalda y restaura solo | Cumple | 1 contenedor pequeño (Python sin dependencias, sin puertos) |
| `cron` del equipo con scripts | Parcial: depende de la máquina de cada integrante | Cumple | Ninguno, pero no se crea con `make up` |
| La API respalda y restaura | Cumple | No cumple: necesita escribir y exponer endpoints | Ninguno |

**Selección: contenedor `backup`.** Se crea y destruye con el resto del entorno (QA-05) y es el único con acceso de escritura al volumen; las instancias de la API siguen en solo lectura.

| Evento | Qué hace el contenedor `backup`, sin intervención |
|---|---|
| Aparece una versión nueva válida | La copia a `store/backups/orders-<versión>.json` |
| El archivo desaparece, es ilegible o inválido | Restaura la última copia válida |
| Los datos son válidos pero distintos del respaldo de su versión | Actualiza el respaldo de esa versión (es una actualización, no una pérdida) |
| Tras restaurar | Registra el resultado y la duración. Si la copia falló, la siguiente revisión lo detecta y restaura de nuevo |

La pérdida de datos para la prueba (PR-04) se provoca con `make corrupt` (deja el archivo inválido) o `make delete-data` (lo borra); la recuperación ocurre sola y se comprueba en los logs de `backup`. La comparación de versión y contenido contra el respaldo es la evidencia de la prueba, no un paso del sistema.

**Diferencia con AWS:** `store/backups/` está en el mismo equipo, así que protege ante la pérdida del archivo (QA-02) pero no ante la pérdida del disco. Se declara como limitación; la carpeta queda fuera del repositorio (`.gitignore`).

## 8. Despliegue, versionado y rollback

### 8.1 Infraestructura como código

**Selección: `docker-compose.yml` + `Makefile`.** Un comando crea todo (`make up`) y otro lo destruye (`make down`). Cumple QA-05 (≤ 10 min, sin pasos manuales fuera de las instrucciones) con solo Docker instalado.

| Comando | Qué hace |
|---|---|
| `make up` | Construye la imagen, crea red y volumen, carga datos, levanta HAProxy y las 2 réplicas |
| `make down` | Elimina contenedores, red y volumen |
| `make deploy TAG=v2` | Despliega una versión nueva al lado de la actual, sin cortar el servicio (§8.2) |
| `make corrupt` / `make delete-data` | Dejan inválido o borran el archivo de datos del volumen, para probar la restauración |
| `make test` | Ejecuta las pruebas del [plan de pruebas](7.%20plan%20de%20pruebas.md) |

### 8.2 Versionado y rollback automático

En AWS el rollback lo hace el circuit breaker de ECS (mínimo 100 % de tareas sanas, máximo 200 % durante el despliegue). Compose no lo trae, por lo que se reemplaza por un script que hace lo mismo: levanta contenedores nuevos al lado de los actuales y solo apaga los actuales si los nuevos funcionan.

| Opción | Vuelve solo a la versión anterior | Sin cortar el servicio | Componentes extra |
|---|---|---|---|
| **Script que levanta contenedores nuevos al lado y apaga los viejos si funcionan** | Cumple: los viejos nunca se detuvieron | Cumple | Ninguno |
| Actualizar una instancia a la vez (rolling) | Cumple, pero hay que volver a cambiar la que ya se actualizó | Parcial: durante el cambio hay una sola instancia sana | Ninguno |
| Docker Swarm (`--update-failure-action rollback`) | Cumple | Cumple | Parcial: obliga a pasar de Compose a Swarm |
| Redespliegue manual de la etiqueta anterior | No cumple | No cumple | Ninguno |

**Selección: contenedores nuevos al lado de los viejos.** Equivale al 200 % del circuit breaker: la capacidad nunca baja, y si la versión nueva falla, basta con descartar lo nuevo. Flujo de `make deploy TAG=vN`:

1. Construye `next-api:vN`.
2. Crea 2 contenedores más con la etiqueta nueva (hay 4 corriendo).
3. Espera a que los 2 nuevos queden *healthy* y a que HAProxy ya les esté enviando tráfico.
4. Si funcionan, elimina los viejos y guarda `vN` en el historial de versiones.
5. Si no arrancan, o no quedan sanos en 2 min, elimina los nuevos, imprime sus logs y termina con error. Los viejos siguen atendiendo y el volumen de datos no se toca.
6. Conserva las imágenes de las últimas 5 versiones desplegadas.

**Versión defectuosa para la prueba:** `make deploy TAG=bad BREAK=1` construye una imagen sin el comando `next`, así el contenedor no arranca. No se agrega código de falla a la aplicación.

## 9. Costo

**Viene de:** QA-07.

| Componente | Qué consume |
|---|---|
| Contenedores, HAProxy | CPU y memoria de la máquina local (límites: 0,25 CPU y 256 MB por `api-*`) |
| Volumen y `store/backups/` | Menos de 1 GB de disco |
| Imágenes | Algunos cientos de MB de disco |
| Red | Solo loopback; sin tráfico a internet |

**Gasto total: 0.** `make down` deja 0 recursos activos; las imágenes se borran con `docker image prune`.

## 11. Qué no se prueba en local

Estas diferencias se declaran en las pruebas y en la presentación, como permite el reto:

| Aspecto | Efecto |
|---|---|
| Caída de zona de disponibilidad | No se simula; solo la caída de una instancia (QA-01 queda cubierto) |
| Respaldo en otro servicio | `store/backups/` está en el mismo disco; cubre la pérdida del archivo, no la del equipo |
| Costos reales de AWS | Se identifican por componente en [cloud components §8](4.%20cloud%20components.md), pero no se miden |
| Tiempos | Los valores de QA-01, QA-02, QA-04 y QA-05 se miden en local; en AWS pueden variar (por ejemplo, el arranque de una tarea Fargate) |
