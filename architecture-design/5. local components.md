# Local components — Nodo Ruta (entorno local)

Equivalente local de los [cloud components](4.%20cloud%20components.md). No hay tiempo ni cuenta para desplegar en la nube, así que el desarrollo y las pruebas se hacen en una sola máquina con contenedores. El [diseño arquitectónico](3.%20diseño%20arquitectónico.md) no cambia: cada pieza de AWS se sustituye por una local que cumple el mismo rol y el mismo escenario de calidad.

Valoración: **Cumple** · **Parcial** · **No cumple**.

---

## Resumen de lo seleccionado

| Decisión del diseño arquitectónico | Componente en AWS | Componente local | Configuración |
|---|---|---|---|
| Lógica síncrona | HTTP/REST sobre ALB | HTTP/REST sobre nginx | `GET /pedidos`, `GET /`, `GET /health` |
| QA-01 Redundancia activa (cómputo) | ECS Fargate, 2 tareas | Docker Compose, 2 contenedores (`api-1`, `api-2`) | Misma imagen (`next/api/Dockerfile`, Python 3.12, FastAPI, puerto 8080) |
| QA-01 Redundancia activa (balanceo) | ALB | nginx (proxy inverso) | Comprobación pasiva: `max_fails=2 fail_timeout=5s`; reintenta en la otra instancia (`proxy_next_upstream`) |
| QA-02 Backup & Restore | Copia a S3 con versionado | Carpeta local `backups/` con la versión en el nombre | Script `backup.sh` / `restore.sh`; copia antes de cada cambio de versión de los datos |
| QA-03 Externalized State | EFS | Volumen nombrado de Docker | Montado en solo lectura (`:ro`) en los 2 contenedores |
| QA-04 Rollback automático | ECR + circuit breaker de ECS | Etiquetas de imagen locales + script de despliegue con espera de salud | Imágenes `next-api:v1`, `v2`…; se conservan las últimas 5 |
| QA-05 Infraestructura como código | Terraform | `docker-compose.yml` + `Makefile` | `make up` crea, `make down` destruye |
| QA-06 Monitor / Logging | CloudWatch Logs | `docker logs` / `docker compose logs` | Una línea JSON por solicitud con `instance_id` |
| QA-07 Cost Efficiency | Destrucción con Terraform | Recursos locales: costo 0 | `make down` elimina contenedores, red y volumen |
| CT-01 Sin secretos | SSM Parameter Store | Variables de entorno, sin archivo `.env` versionado | Hoy no hay secretos |
| CT-02 Exposición mínima | Solo el ALB recibe tráfico | Solo nginx publica puerto | `localhost:8000`; los contenedores `api-*` no publican puerto |

**Requisito previo:** Docker (con Docker Compose v2) y `make`. No se necesita cuenta ni conexión a ninguna nube.

## 1. Topología

```
Cliente (curl / navegador / pruebas)
        │  localhost:8000
        ▼
   ┌─────────┐   reintenta en la otra instancia si una falla
   │  nginx  │──────────────┬──────────────┐
   └─────────┘              ▼              ▼
                        ┌───────┐      ┌───────┐
                        │ api-1 │      │ api-2 │      red interna de Compose
                        └───┬───┘      └───┬───┘      (sin puertos publicados)
                            └──────┬───────┘
                                   ▼  (solo lectura)
                        Volumen `orders-data`  ──► backups/orders-<versión>.json
```

## 2. Lógica

El contrato del servicio no cambia respecto a la nube (ver [cloud components §1](4.%20cloud%20components.md)).

| Operación | Respuesta | Cubre |
|---|---|---|
| `GET /pedidos` | Los pedidos y el identificador de versión | RF-01, RF-02 |
| `GET /` | Página de inicio | RF-03 |
| `GET /health` | Estado "ok" | RF-04 |
| Toda respuesta | Header `X-Instance-Id` | RF-05 |

**Identificador de instancia:** en AWS es el ID de la tarea; en local es el nombre del contenedor (`api-1`, `api-2`), que el servicio toma de la variable `HOSTNAME`/`INSTANCE_ID`.

## 3. Cómputo

**Viene de:** 2 instancias sin estado (QA-01), recreación de contenedores (QA-03).

| Opción | 2 instancias de la misma imagen | Reemplazo automático | Crear y destruir con un comando | Costo |
|---|---|---|---|---|
| **Docker Compose** | Cumple | Cumple (`restart: unless-stopped`) | Cumple | 0 |
| Kubernetes local (kind / minikube) | Cumple | Cumple | Parcial: más piezas que instalar y configurar | 0 |
| `docker run` manual | Cumple | No cumple | No cumple | 0 |

**Selección: Docker Compose.** Es lo mínimo que cumple QA-01, QA-03 y QA-05; el reto no exige un orquestador concreto.

**Diferencia con AWS:** las 2 instancias corren en la misma máquina, por lo que no se prueba la caída de una zona de disponibilidad; solo la caída de una instancia, que es lo que pide QA-01.

## 4. Punto de entrada y salud

**Viene de:** balanceador que deja de enviar solicitudes a la instancia que falla, redundancia activa (QA-01).

| Opción | Reparte entre las 2 instancias | Deja de usar la instancia caída | Configuración sencilla en Compose |
|---|---|---|---|
| **nginx** | Cumple | Cumple, de forma pasiva (ver abajo) | Cumple |
| HAProxy | Cumple | Cumple, con sondeo activo (`check inter 5s fall 2`) | Cumple |
| Traefik | Cumple | Cumple, con sondeo activo | Parcial: configuración por etiquetas, menos explícita |

**Selección: nginx.** Es el más conocido y el más simple de configurar. La versión libre no sondea `/health` por sí sola: detecta fallos en las solicitudes reales.

```
upstream api {
    server api-1:8080 max_fails=2 fail_timeout=5s;
    server api-2:8080 max_fails=2 fail_timeout=5s;
}
location / {
    proxy_pass http://api;
    proxy_next_upstream error timeout http_502 http_503 http_504;
}
```

- **Cómo cumple QA-01:** si una instancia no responde, nginx reintenta la misma solicitud en la otra, así que el cliente no ve el error (≥ 99 % de éxito). Tras 2 fallos, nginx deja de enviarle solicitudes durante 5 s y la vuelve a probar sola.
- **Diferencia con AWS:** sin tráfico, nginx no detecta la caída; es indiferente porque nadie consulta. La medida "≤ 10 s hasta dejar de enviar solicitudes" se verifica con tráfico continuo durante la prueba.
- **Salud visible:** cada contenedor lleva su propio `healthcheck` de Compose contra `/health` (cada 5 s, 2 fallos); `docker compose ps` muestra cuál está *unhealthy*. Es informativo; no gobierna el reparto de nginx.
- **Riesgo:** nginx resuelve los nombres `api-1` y `api-2` al arrancar. Si un contenedor se recrea con otra IP, hay que recargar nginx (`nginx -s reload`) o usar el resolvedor de Docker (`resolver 127.0.0.11`). Se valida en las pruebas.

## 5. Persistencia

**Viene de:** Externalized State (QA-03), almacenamiento compartido de solo lectura.

| Opción | Compartido entre instancias | Sobrevive al contenedor | Sin cambio de código |
|---|---|---|---|
| **Volumen nombrado de Docker** | Cumple: montable en ambos | Cumple | Cumple: se lee como carpeta |
| Bind mount a una carpeta del equipo | Cumple | Cumple | Cumple, pero depende de rutas y permisos de cada máquina |
| Carpeta dentro de la imagen | Cumple | No cumple: se pierde al recrear | Cumple |

**Selección: volumen nombrado `orders-data`**, montado en `/data` con `:ro` en ambos contenedores. El archivo inicial es `next/api/data/orders.json` (6 pedidos y su versión), que se carga al volumen con `make load-data`.

## 6. Respaldo y restauración

**Viene de:** Backup & Restore (QA-02).

| Paso | Procedimiento local |
|---|---|
| Respaldo | `make backup`: copia `orders.json` a `backups/orders-<versión>.json` (fuera del volumen de trabajo) |
| Alteración (prueba) | Modificar una copia del archivo en el volumen para simular la pérdida o alteración |
| Restauración | `make restore VERSION=<versión>`: copia el respaldo de vuelta al volumen |
| Verificación | Comparar versión y contenido (`diff` / `sha256sum`) contra el respaldo; el tiempo se mide con `time` (≤ 5 min) |

**Diferencia con AWS:** `backups/` es una carpeta del mismo equipo, así que protege ante la alteración del archivo (QA-02) pero no ante la pérdida del disco. Se declara como limitación; la carpeta queda fuera del volumen y del repositorio (`.gitignore`) salvo el respaldo de ejemplo.

## 7. Observabilidad

**Viene de:** Monitor / Logging (QA-06).

| Opción | Registros por instancia | Consulta rápida | Componentes extra |
|---|---|---|---|
| **Logs de Docker (`docker compose logs`)** | Cumple: un flujo por contenedor | Cumple (`logs api-1`, filtrar con `grep`) | Ninguno |
| Loki + Grafana | Cumple | Cumple | Cumple, pero agrega 2 servicios |
| Archivos de log en el volumen | Parcial | Parcial | Escritura en un volumen que debe ser de solo lectura |

**Selección: logs de Docker.** Cada instancia escribe por la salida estándar una línea JSON con `instance_id`, ruta y código de respuesta. El estado de salud se ve con `docker compose ps` (columna *healthy*) y en los logs de nginx.

## 8. Despliegue, versionado y rollback

### 8.1 Infraestructura como código

**Selección: `docker-compose.yml` + `Makefile`.** Un comando crea todo (`make up`) y otro lo destruye (`make down`). Cumple QA-05 (≤ 10 min, sin pasos manuales fuera de las instrucciones) con solo Docker instalado.

| Comando | Qué hace |
|---|---|
| `make up` | Construye la imagen, crea red y volumen, carga datos, levanta nginx y los 2 contenedores |
| `make down` | Elimina contenedores, red y volumen |
| `make deploy TAG=v2` | Despliega una versión con rollback automático (§8.2) |
| `make backup` / `make restore` | Respaldo y restauración (§6) |
| `make test` | Ejecuta las pruebas del [plan de pruebas](7.%20plan%20de%20pruebas.md) |

### 8.2 Versionado y rollback automático

En AWS el rollback lo hace el circuit breaker de ECS. Compose no lo trae, por lo que se reemplaza por un script.

| Opción | Vuelve solo a la versión anterior | Componentes extra |
|---|---|---|
| **Script `deploy.sh` con etiquetas de imagen** | Cumple | Ninguno |
| Docker Swarm (`--update-failure-action rollback`) | Cumple | Parcial: obliga a pasar de Compose a Swarm |
| Redespliegue manual de la etiqueta anterior | No cumple | Ninguno |

**Selección: script con etiquetas.** Flujo de `make deploy TAG=vN`:

1. Construye `next-api:vN` y guarda cuál es la etiqueta actual.
2. Actualiza los contenedores a `vN`.
3. Espera hasta 2 min a que ambos queden *healthy*.
4. Si alguno no lo logra, vuelve a la etiqueta anterior y termina con error; el volumen de datos no se toca.
5. Conserva las últimas 5 etiquetas.

## 9. Costo

**Viene de:** QA-07.

| Componente | Qué consume |
|---|---|
| Contenedores, nginx | CPU y memoria de la máquina local (límites: 0,25 CPU y 256 MB por `api-*`) |
| Volumen y `backups/` | Menos de 1 GB de disco |
| Imágenes | Algunos cientos de MB de disco |
| Red | Solo loopback; sin tráfico a internet |

**Gasto total: 0.** `make down` deja 0 recursos activos; las imágenes se borran con `docker image prune`.

## 11. Qué no se prueba en local

Estas diferencias se declaran en las pruebas y en la presentación, como permite el reto:

| Aspecto | Efecto |
|---|---|
| Caída de zona de disponibilidad | No se simula; solo la caída de una instancia (QA-01 queda cubierto) |
| Respaldo en otro servicio | `backups/` está en el mismo disco; cubre la alteración, no la pérdida del equipo |
| Costos reales de AWS | Se identifican por componente en [cloud components §8](4.%20cloud%20components.md), pero no se miden |
| Sondeo activo de salud | nginx libre solo detecta fallos con tráfico real; el sondeo periódico de `/health` no lo hace el balanceador |
| Tiempos | Los valores de QA-01, QA-02, QA-04 y QA-05 se miden en local; en AWS pueden variar (por ejemplo, el arranque de una tarea Fargate) |
